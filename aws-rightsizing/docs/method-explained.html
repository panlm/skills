降配建议是怎么算出来的

示例账号 123456789012 · ap-east-1 · 观测窗口 2026-08-10 → 2026-09-09（30 个完整业务日，业务时区 UTC+8）· 本文数字取保守档

结论不是"看着 CPU 低就砍一半"。每一类资源都走同样的两步：先从实测指标反推它真正需要多少资源，再在满足全部硬性约束的规格里挑最便宜的那个。两步都是确定性计算，同一份输入必然得到同一份输出，结论可复算。

不同的是每类资源的"第一判据"不一样：EC2 看 CPU 与内存利用率，RDS 看活跃会话数，Redis 看单线程引擎 CPU 与 maxmemory 占用，MSK 看请求处理线程空闲率。所以本文按服务分章，每章都能单独读完。

先说清三条口径

  1. 所有金额都是公开按需价（On-Demand）的理论值，不含实际账单。被预留实例（RI）或 Savings Plan 覆盖的资源，降配后账单不一定立刻下降——折扣会转移到其他资源或在承诺期内搁置。百分比的分子分母都是按需理论值，分母不是实际账单。
  2. 只做同形态降配：不改架构、不换 CPU 架构（x86 ↔ Arm）、不降可用性等级。不含 Serverless 化、Spot、减副本、减分片、减 broker、RDS 多可用区改单可用区。
  3. 指标缺失时一律不给建议，而不是按 0 处理。少省钱是可接受的，误判导致故障不可接受。但"不适用"和"缺失"要分开——例如非突发机型本来就不发布 CPU 信用指标，那不是数据缺口，不该因此关闭它的降配路径。

共通机制：两档预设、需求反推、四种结论

两档预设的全部差别，就是"留多少余量"

反推需求量时，把实测利用率除以一个目标利用率——即"降完之后利用率不要超过这个值"。目标越低 = 余量越大 = 建议越保守。

阈值保守档 conservative激进档 aggressive用在哪里
CPU 目标（持续项）40%60%EC2 / RDS 的 CPU 轴、Redis 的引擎 CPU
CPU 上限（峰值项）60%85%EC2 / RDS 的峰值项
内存目标（持续项）50%70%EC2 内存轴、Redis 可用内存反推
内存上限（峰值项）70%85%EC2 内存峰值项
单次降幅上限2 倍3 倍EC2 的 vCPU 与内存；托管服务的 vCPU（Redis 内存例外，见该章）
MSK CPU 目标40%40%两档相同：MSK 的机型阶梯太稀疏，调它不改变结论
采样点分档线168 点168 点业务时段有效小时数低于此值 ⇒ 仍给建议，置信度降 low

两档按风险偏好命名，不按"生产 / 非生产"。原因：这套判据无法验证一台机器到底是不是生产环境，而贵方直接知道自己能接受多激进。两档结果都会交付，对外沿用保守档。

需求反推：两项取 max

持续项防"日常不够用"，峰值项防"尖峰被打满"。取两者的大值，峰值项不可省略：

需要的量 = max(  ceil(现有量 × 持续利用率 ÷ 目标) ,  ceil(现有量 × 峰值利用率 ÷ 上限)  )
                     └─── 持续项 ───┘            └──── 峰值项 ────┘

ceil 是向上取整：ceil(6.24) = 7。机器不卖半颗核，算出 6.24 就必须给 7——宁可多给，不能少给。

各服务的"持续"与"峰值"取自不同指标，口径也不完全一样（RDS 的峰值项取 Maximum 序列的 p95，而 EC2 取 max）。逐服务在各自章节里写明，这里只讲公式形状。

四种结论：先看结论列，再看金额

结论触发含义
downsize-candidate全部门槛通过且候选池非空可降配，给出目标规格与月省金额
已合理配置候选池为空，或某道前置门槛未过这一行没有可降的目标。报告必须写出是哪一条约束绑定——六种成因见下一节，动作完全不同
upsize-candidate持续项反推需求 > 现有规格，或 CPU 信用余额触底，或已在付超额信用费当前规格已经不足，方向相反。本套判据不产出升配目标机型——选型需要容量规划输入（增长率 / SLA / 峰值形态）
blocked命中该服务的独立否决项（OOM、存储耗尽、驱逐、副本滞后、副本不足…）有明确的技术原因不能降。"缩不了"不等于"规格不足"，两者动作不同
metric-missing关键指标缺失且该指标对本资源确实适用没有能力判断。必须早于"已合理配置"，否则"判不了"会被伪装成"无需优化"
excluded本版本不评估的形态（加速计算机型、Aurora Serverless v2、Memcached）诚实排除，不猜一套未验证的判据
为什么升配只看持续项。拿峰值项反推"规格不足"，一台 CPU 持续 7.25%、偶发峰值 98% 的闲置小机器会被判成需要扩容。峰值项存在的目的是限制降配幅度，不是判断当前规格不足。

采样量不足 ⇒ 降置信度，不是不出结论

业务时段有效点数低于 168 时照常产出建议，置信度降为 low，并在阻断项里写明实际点数与占门限比例。只有点数为 0 或缺失才判 insufficient-data——那是"无"，不是"少"，p95 无从计算。

为什么改成分档：旧写法在门限之下整段短路，把否决项一起压掉了。实测有一个集群的 UnderReplicatedPartitions = 27、一个 Redis 复制组的 ReplicationLag = 23.88s，都因此没出现在报告里，报告只写了"点数不足"——而否决项读的是持续值与峰值，拿采样量去挡它没有依据。

删除与停机例外。这条分档只放开降配路径（可回滚）。闲置删除与定时停机的动作不可回滚，采样点数保持硬门槛。

两个容易对不上的口径

p95 是"最近秩"，不插值

排序后取下标 floor((n − 1) × 0.95)，取的是窗口内真实出现过的那个点，不在两点之间插值。

两个后果：① 相对插值口径系统性偏低，方向上让定档更紧；② p95 永远取不到最大值，所以峰值判据必须另读 max。拿 numpy 或控制台的 p95 来对会差一点，这不是缺陷。

采样周期不丢峰值，发布环节才丢

实测 6 台机器，period=3600 与 period=60 得到的 Maximum 完全相同——Maximum 取周期内已发布点的最大值，不做平均。

峰值损失发生在发布：EC2 基础监控每 5 分钟发布一次，且发布值已经是这 5 分钟的平均。所以"开详细监控"能解锁尖峰型负载的重评，"把 period 调小"不能。

窗口按业务本地午夜对齐。不对齐会让同一份数据被切进不同时段档——实测同一实例 peak_cpu 在 18.18% 与 10.59% 之间摆动，足以改变反推出的核数。对齐后满窗口资源的点数是可精确预测的整数：业务时段 = 工作日数 × 11、非业务时段 = 工作日数 × 13、周末 = 周末天数 × 24，三者之和 = 窗口天数 × 24。本次 30 天窗口实测 242 / 286 / 192，合计 720，闭合。

共通机制：候选池为空的六种成因

"已合理配置"这四个字对贵方没有信息量——下一步动作取决于是哪条约束绑定的。所以候选池为空时，报告必须写出成因，且这六种成因的动作完全不同：

成因含义贵方的下一步
没有更便宜的候选已经在该区域该形态的价目地板上无事可做。补监控、延长窗口都不会改变结论
更便宜的全部跨 CPU 架构例如当前是 Graviton，唯一更便宜的是 x86这是硬约束不是阈值。若业务确认可接受跨架构迁移，需另立评估（重新编译 / 镜像 / 兼容性）
需求量超过所有更便宜候选实测负载本身要求这么多核规格是合适的。要再降只能先降负载
被降幅地板挡住更便宜的候选都低于"一次最多砍 N 倍"这道地板这是策略选择：换激进档（2 倍 → 3 倍）就可能有候选，或分两次降
更便宜的候选装不下内存核数够但内存不够看内存需求的来源是否可调（如 Redis 的数据量、数据库缓冲区参数）
唯一装得下的候选被排除例如该实例类不支持 Performance Insights，而 PI 是 RDS 的第一判据报告会量化放弃的金额：若接受丢失 PI 可额外省多少，但下一轮该行的第一判据不可得

这一节是本轮判据的主要改进之一。改进前这六种情形共用一句笼统话，而那句话在后四种成因下是错的——它会让贵方去补一份补了也不会产出建议的监控，再等一个 30 天窗口。

EC2

第一判据：CPUUtilization 与 CloudWatch Agent 的 mem_used_percent

CPU 与内存各自走"两项取 max"，持续项取业务时段 Average 序列的 p95，峰值项取 Maximum 序列的 max——EC2 上的尖峰是真实业务负载，不能按 p95 平滑掉。

需要的 vCPU = max(  ceil(现有 vCPU × CPU_p95 ÷ CPU目标) ,  ceil(现有 vCPU × CPU_max ÷ CPU上限)  )
需要的内存 = max(  ceil(现有 GiB  × 内存_p95 ÷ 内存目标) ,  ceil(现有 GiB  × 内存_max ÷ 内存上限)  )

内存另有三条特殊规则

情形处理为什么
没有内存指标 内存需求 = 当前规格（内存维度锁死不动），置信度上限 medium 此时只有核数有余量可降。不按 0 处理，也不拍一个下限
有内存指标 完全按实测反推，不设"至少要 N GiB"的绝对下限 拍一个绝对下限等于在不了解这台机器真实内存画像的情况下替它做假设——会同时对小实例过度保护、对大实例仍然放行
所有情形 候选内存不得低于 ceil(现有 GiB ÷ 降幅上限) 见下：内存 p95 被系统性压低，比 CPU 更需要这道地板
为什么内存 p95 是被低估的

CloudWatch Agent 的 mem_used_percent = mem_used ÷ mem_total，不含可回收的 page cache——页缓存被算进"未使用"。但那部分缓存对 I/O 密集型负载有实际价值：换到内存只剩一半的机型上，缓存命中率下降、磁盘 I/O 上升，而这件事在降配前的 mem_used_percent 里完全看不见。CPU 侧没有这个对应的偏差源。

选型：十道硬性门槛，全过才算候选

1. CPU 架构一致x86 不换成 Arm，反之亦然
2. 非过时机型族已有更新代次替代的族被排除
3. 排除 *-flex 族flex 的可持续 CPU 低于标称，但接口报"非突发型"，会被误当满容量机型
4. 该区域真的能开按当前区域现查可用机型集合，不复用别的区域
5. 本地盘属性一致带 NVMe 本地盘的不换成不带的
6. 同族不许倒退代次c6i 不会被换成 c5
7. 机型分类合规通用 / 计算优化 / 内存优化，或与原分类相同
8. EBS 吞吐足够实测吞吐需求缺失时直接放弃，不当 0
9. 单价必须更低否则不构成优化
10. 降幅不超上限保守档：vCPU 与内存都不得低于现有的 1/2

剩下的候选里取 vCPU ≥ 需求 且 内存 ≥ 需求 的，按单价升序选第一个。月省 = (现单价 − 目标单价) × 730 × 台数。

取价按 (机型, UsageOperation) 复合键，不只按机型。同一 m5.xlarge 在本区域的按需价：Linux $0.248、RHEL $0.306、Windows $0.432、Windows+SQL Enterprise $1.932——最多差 7.79 倍。只按机型取价会让非 Linux 实例的成本被严重低估，节省金额完全失真。降配不改变操作系统与授权，所以候选沿用当前实例的 UsageOperation。

第 10 道门（降幅上限）为什么必须存在

目标利用率只能保证"按已经测到的负载不越界"，它管不了两类风险：

  1. 5 分钟以内的尖峰不可见。基础监控每 5 分钟发布一次且已做平均，一次 30 秒的 100% 尖峰在数据里只显示约 10%。
  2. 30 天窗口看不到月度 / 季度周期（月结批处理、季度对账）。

窗口错过周期性峰值时，4 核砍到 1 核就是 4 倍不够用。这两条理由与指标种类无关，所以内存也有同样一道地板。

一个诚实的边界：向上取整会在小规格上吞掉两档预设的差别。现有内存 ≤ 4 GiB 时，两档算出的内存地板完全相同，"更保守"这句承诺在内存这一维上兑现不了；8 GiB 起才开始分道。CPU 侧在小核数上同理。

突发型（T 系列）是可选的第二条路线

T 系列更便宜，但按 CPU 信用模型工作。要给出 T 系列建议，除十道门外还要额外满足三条：

  • 窗口内 CPUSurplusCreditsCharged 必须为 0——已经在付超额信用费说明现规格就不够了。
  • 标称核数 ≥ 峰值项算出的核数——T 系列的突发上限就是标称核数的 100%，不能靠信用突破。
  • 标称核数 × 基线% × 0.8 ≥ 实际已用核数——基线之内还要留 20% 余量，保证不靠消耗信用就能扛住日常负载。

两条路线互斥、不可相加：路线一全用非突发机型，任何场景都适用；路线二逐台取更省的一方，前提是逐台确认能接受突发信用模型。

"当前机型不是 T 系列"不等于"信用指标缺失"。非突发机型结构性不发布 CPUSurplusCreditsCharged，把它当"缺失"去 fail-closed，会让突发路线在整支机队上永久不可达——实测 29 台里 25 台的突发列因此被压掉过。现在先判适用性、再判缺失。

CPU 信用余额触底（T 系列专有，优先级高于持续项）

突发型机器的信用一旦耗尽，CPU 就被限流到基线——此时 CPUUtilization 是被压住的，持续值不能用于定档。所以这条必须排在持续项之前：

触底 = 窗口内余额最小值 ≤ 窗口内余额最大值 × 10%     （或窗口内恒为 0）
     ⇒ upsize-candidate，且两条降配路线全部压掉

分母取"窗口内观测到的最大余额"而不是理论信用上限，是为了让 EC2 与 RDS 共用同一套算法。实测分离度很干净：触底样本 0.00%–0.14%，健康样本 85.07%–99.91%，中间没有任何观测点。

反方向的信号：非突发机型上出现了信用余额序列，说明这台机器在窗口内改过规格。该余额测自另一个规格、不作为否决依据，但本行的利用率百分比混合了两个规格的采样，报告会标出来要求人工复核。

三个真实例子

例 1：ec2-stg-01 — 建议不是"缩"，是"换到匹配的形态"

实测 c7i.8xlarge（32 核 / 64 GiB）：CPU p95 4.82%、峰值 13.11%；内存 p95 66.29%、峰值 67.23%。

vCPU 需求 = max( ceil(32 × 4.82%  ÷ 40%) , ceil(32 × 13.11% ÷ 60%) ) = max(4, 7) = 7 核
内存需求 = max( ceil(64 × 66.29% ÷ 50%) , ceil(64 × 67.23% ÷ 70%) ) = max(85, 62) = 85 GiB   ← 比现有 64 GiB 还多

这台机器CPU 严重过剩、内存其实偏紧。选出的 r5.4xlarge（16 核 / 128 GiB）核数砍一半、内存翻倍，单价反而更低 —— 月省 $349.23（当前 $1,324.51/mo）。只按"内存用了 66%，别动"的直觉判断，这台就漏掉了。

这也解释了第 7 道门为什么允许跨机型分类。分类本质上编码的是 vCPU:内存 比例（计算 1:2 / 通用 1:4 / 内存 1:8）。实测比例偏离当前族时，跨分类才是正解——报告里每一条分类变更都显式标出，供人工复核。

CPU  持续项 = ceil(4 × 7.25%  ÷ 40%) = 1 核
CPU  峰值项 = ceil(4 × 98.03% ÷ 60%) = 7 核   ← 取 max，需求 7 核 > 现有 4 核
内存 峰值项 = ceil(8 × 72.81% ÷ 70%) = 9 GiB  ← 也高于现有 8 GiB

需求量比现有规格还高，没有任何候选能通过，判为"已合理配置"、不给建议。

注意它是"已合理配置"而不是 upsize-candidate：把它推高的是峰值项，持续项远低于现有规格。区别很实际——如果报成升配候选，贵方会去为一台其实很闲的机器扩容。

判据顺序（短路链，命中一环立即出结论）

  1. 规格未知 / 价格未知 → 不给建议。没有权威单价时，绝不退回"最小够用"的猜测选型——实测无价格时会推荐出比现状更贵的机型。
  2. 加速计算机型（G/P/Inf/Trn）→ 排除。受限资源是加速器，默认 CloudWatch 没有加速器利用率指标。
  3. 关键指标缺失（CPU / EBS 吞吐）→ metric-missing。必须早于"已合理配置"，否则"没能力判断"会被伪装成"无需优化"。
  4. CPU 信用余额触底（T 系列）→ upsize-candidate。必须早于持续项：被限流的机器持续值必然偏低。
  5. 候选池非空 → downsize，给出目标机型与金额。
  6. 持续项已超现有规格 → upsize-candidate；否则 → 已合理配置。

EBS 与快照

卷

  • gp2 → gp3 全量给出：同容量下 gp3 单价更低。原容量 > 334 GiB 时基线 IOPS 已超 3000，转 gp3 必须显式配置 IOPS，这条会写进阻断项。
  • 未挂载卷（state=available）进闲置清单，动作是删除。
  • 容量是否过大判不了：需要 CloudWatch Agent 的 disk_used_percent，且挂载点与卷的映射必须可靠。缺任一项就不产出容量缩减建议，会列进数据缺口。

快照：只列事实，不判年龄

报告会列出快照清单、容量、创建日期、月额，但不产出删除建议——该不该删取决于 RPO 与合规留存要求，这两样都不在任何 API 里。

同一个"很旧"的快照可能是审计要求的留存副本；"很新"的可能是某个已删除卷唯一的恢复点。"源卷已删除"更不能当删除信号——那恰恰是快照可能是唯一剩余副本的情形。

删卷与转存储类型互斥。任何走删除路径的卷都不再出 gp2→gp3 行：前者省全额、后者只省差价，相加就是高估。实测一个未挂载的 gp2 卷曾同时出删除行 $3.60/mo 与转换行 $0.72/mo，两个动作互斥却都进了合计。

RDS

第一判据是 DBLoad（活跃会话数），CPU 是并行的第二判据

为什么不只看 CPU：数据库的瓶颈通常不是 CPU 时间而是并发活跃会话数。Performance Insights 的 db.load.avg（AAS）直接对标 vCPU 数，是数据库容量的正确刻度。

但两轴是并行关系，不是主备：required_vcpu 取两轴的大值。实测一台 db.m6g.xlarge 的 DBLoad p95 差 0.328 没跨阈值，按旧写法判"已合理配置"，而它的 CPU 持续 p95 是 69.64% —— 那是升配候选。

三个 RDS 专有的口径

CPU 峰值项取 Maximum 序列的 p95，不是 max

RDS 的 CPU 尖峰可证明来自托管平面的维护动作（备份窗口、自动小版本升级）。实测一台常态 4.00% 的库出现单峰 88.33%，按 max 反推需 3 vCPU 而它只有 2。

按 max 判，12 台里激进档只剩 2 台可降、保守档 0 台。EC2 侧保持取 max 不变——那里的尖峰是真实业务负载。

FreeableMemory 必须采 Minimum

空闲内存越多越安全，危险点在最小值那一侧。用 Maximum 或 Average 的 p95 是取错了方向，会把危险实例判成安全。

而且要取全窗口而非业务时段：内存低点常落在备份 / 批处理的非业务时段。

内存需求怎么反推

需要的内存 = (实例内存 − FreeableMemory 最小值) ÷ (1 − 15%)

分子是实测的"已用内存上界"，除以 (1 − 15%) 是把 OOM 阻断那道地板作为余量留出来——一个候选"装得下"的定义就是降配后 FreeableMemory 仍高于那道地板，所以不再叠加额外余量。

这个值是真实工作集的上界，方向保守

数据库引擎的缓冲区（MySQL innodb_buffer_pool_size / PostgreSQL shared_buffers）有意占满可分配内存，FreeableMemory 报的是 MemAvailable。所以一个配置正确的库按设计就是低 freeable。这条证据支持"缩不了"，不支持"需要更大的实例"。代价是系统性少省：若变更时同步下调缓冲区参数，可以选更小的实例类——报告会把这句写进每一条 RDS 建议。

选型的两条 RDS 专有规则

  • 取价必须带部署形态。Multi-AZ 是独立的计费项、单价约为单可用区的 2 倍。实测同一支机队里两台同规格 db.m6g.2xlarge，单价分别是 $0.92 与 $1.84/h。只按实例类取价会把 Multi-AZ 实例的成本算便宜一半，节省金额随之失真。
  • 已开 PI 的实例，不支持 PI 的实例类会被排除。但报告会量化放弃的金额：那个更便宜的候选能多省多少、代价是下一轮失去第一判据。取的是"本来装得下、只因排除才没选中"的那一个——否则会报出一笔本来也拿不到的钱。

PI 不可得有两种成因，动作不同：「未开启」改个开关即可；「该实例类结构性不支持」要换机型才能拿到。报告分开写这两种，不写成笼统的"缺 db.load.avg"。

一条不改结论、但要求人工核对的校验

DBLoad 的 Maximum 序列 p95 单独反推若超过现有 vCPU，报告会降低置信度并要求去 PI 控制台核对，但不改 verdict。原因：两条序列跨度实测 5 倍到 1370 倍，而成因在"PI 按 1 秒发布"与"Average 被 SampleCount 稀释"之间无法从聚合值判定——拿不到就不能算。本次 15 台里 3 台命中这条注记。

Redis / Valkey（ElastiCache）

CPU 必须用 EngineCPUUtilization，内存必须用 DatabaseMemoryUsagePercentage

为什么不用 CPUUtilization：Redis 是单线程处理命令的。节点整机 CPU 里混了后台线程（快照、复制、网络），用它定档会系统性误判。EngineCPUUtilization 才是那个会先打满的线程。

先判引擎，再判指标。这两个指标只有 redis / valkey 发布。Memcached 不评估——它多线程、两个都不发布，需要另一套（CPU 看 CPUUtilization、内存看 BytesUsedForCache 对节点上限），而那套指标的刻度未经实测。发明一套未验证的判据比诚实排除更糟，而报成"缺指标"更糟——那会让贵方去补一个不可能存在的指标。

判据顺序

#判据结论

为什么两条否决项排在"引擎"之前："这个缓存正在淘汰键"对 Memcached 同样成立，是有效阻断，与能不能降配无关。而"引擎不评估"要排在候选池探针之前——"本版本不评估"比"没有更便宜的候选"靠前，后者会暗示已经评估过了。

否决项判"持续成立"，不判"曾经出现过一次"。一次 failover 或备份快照造成的尖峰不应该否决整个窗口。本机队多个复制组的 ReplicationLag 持续值都远低于 1 秒，而窗口内最大值达 20.2s / 26.0s；按最大值否决，任何做过 failover 或备份快照的复制组降配路径就永久关闭了。尖峰不否决 ≠ 尖峰不报告——最大值会写进阻断项，让维护事件保持可见，并要求降配前确认该尖峰不是容量不足所致。
Evictions 与 ReplicationLag 的缺失处理不对称，这是有依据的。Evictions 每个节点都发布，缺失就是真缺失 ⇒ 不给建议。ReplicationLag 只在存在副本时才有意义 ⇒ 按"是否存在副本"分流：有副本却没有序列 = 采集缺口，仍然不给建议；无副本 = 不适用，放行。副本存在性由节点 ID 的分片-成员结构推出，不用节点数代替——"3 分片 × 1 节点"（节点数 3、无副本）是合法配置。

可用内存怎么算——这一步很容易算错 1.33 倍

已用可用内存 = 节点内存 × (1 − reserved-memory-percent) × DatabaseMemoryUsagePercentage ÷ 100
候选须满足   = 候选节点内存 × (1 − reserved) ≥ 已用可用内存 ÷ 内存目标(50%)

DatabaseMemoryUsagePercentage 是相对 maxmemory 的百分比，而 maxmemory = 节点内存 × (1 − reserved)，不是节点内存的百分比。所以这里是乘 (1 − reserved)；写成除会得到节点总内存口径，把需求量放大约 1.33 倍。reserved-memory-percent 是集群参数（不是指标），未显式设置时按 AWS 默认 25% 取。

节点内存必须取 pricing 接口的真实值，不能用 EC2 同名机型映射。实测 cache.t3.medium 真实内存 3.09 GiB，映射到 EC2 t3.medium 会得到 4.00 GiB，偏高 29%；而 DatabaseMemoryUsagePercentage 是相对真实节点内存的百分比，基数错则绝对量全错。

取价也有两个坑：① 同一个 cache.t3.medium 在价目表里有三个价（正常节点用量 / 两档扩展支持），随机取到会高估 60% 或低估 21%；② Valkey 的价格比 Redis 低约 20%，而两者的计费用量类型逐字相同——只按机型取价会拿 Valkey 的价格去算 Redis 集群，低估 20%。所以取价键是"机型 + 引擎"，与 EC2 侧同构。

一个刻意的例外：内存不设降幅地板

EC2 侧对 vCPU 和内存都有"一次最多砍 N 倍"的地板。Redis 的内存维度没有这道地板，两个理由：

  1. 结构上不可满足。ElastiCache 的节点内存不是 2 的幂（0.50 / 1.37 / 3.09 / 6.38 GiB），相邻档比值 2.74 / 2.26 / 2.07 全部大于 2。保守档的 2 倍地板从 cache.m6g.large 往下要求候选 ≥ 3.19 GiB，而下一档只有 3.09 GiB——差 3%，永久挡死。实测按该地板筛，11 个复制组全部选不出目标、合计 $0，而失败原因还会被写成"装不下"，诊断信息指向错误方向。
  2. 立论不成立。那道地板的理由是"mem_used_percent 不含可回收 page cache、会压低内存 p95"。而 DatabaseMemoryUsagePercentage 是相对 maxmemory 的权威利用率，没有那个盲区。
代价是"降得深"，所以有一道额外的护栏

目标落在同架构价目阶梯的最底档时，强制置信度 low 并写明：倍数余量看着充足但绝对量极小，触底后估错了没有退路（不能再降，任何数据量增长只能升配）。本次 13 个复制组里有 6 个命中这条护栏——它们的数据量确实极小（已用可用内存 0.011–0.022 GiB），但这类建议必须按业务增长预期人工复核，不能只看利用率百分比。

MSK

CPU 是两个指标逐点相加，且同一命名空间内刻度不统一

为什么不能分别算 p95 再相加：Kafka broker 的 CPU 判据是 CpuUser + CpuSystem，而两个序列各自的 p95 之和 ≠ 和的 p95。正确做法是在查询里用表达式 m1+m2 逐点相加，再做时段聚合。

实测对比（某 broker，业务时段）：逐点相加得持续 p95 5.45；分别算 p95 再相加得 5.495。本例只差 0.8%，是因为两个序列的峰值恰好同时出现——这是运气，不是通例。

EKS

EKS 的浪费主体不在节点利用率，而在 request 超配把节点池撑大。所以这一章的输出形态和别处不同：

  • 节点级建议只出现在节点池聚合行上，不逐节点出。托管节点组的机型只能整池改，逐节点降配是不可单独执行的动作，且与聚合行的节省额重复计数。
  • Karpenter 给的是 NodePool 的 requirements / limits 建议，不是具体机型——机型由 NodePool 决定。两者在报告里区分标注。
  • pod request 必须按 K8s 的调度口径算：max(Σ 普通容器, 各 init 容器的最大值) + pod overhead。只取第一个容器或逐容器简单求和都会低估——实测一个两容器 250m+50m、init 2 核、overhead 100m 的 pod，简单求和得 300m，调度口径是 2100m，差 7 倍。
  • 装箱计算必须把 DaemonSet 与业务 pod 分开：DaemonSet 的 request 是每节点固定开销，随节点数增减，混进总量会系统性高估所需节点数。
缺 Container Insights 不等于 pod 级分析全部不可得

六项分析里有四项是"配置比配置"，只需 kubectl：① request 对可分配量的预订率、② 装箱理论最少节点数、③ 空节点组 / 未调度 pod、④ Fargate request 超配。第 ⑤ 项 HPA minReplicas 能读到配置，但判断"是否过高"需要历史负载。只有第 ⑥ 项——pod 实际利用率的历史曲线——真正无法替代。

实测某集群 Container Insights 一条指标都没有，纯 kubectl 仍得出：节点可分配 9.65 vCPU / 34.08 GiB，pod requests 7.79 vCPU / 11.56 GiB ⇒ CPU 预订率 80.7%、内存预订率 33.9%，两者差 2.4 倍 ⇒ 机型错配信号明确（该换计算优化族而非通用族）。这个结论不需要任何历史指标。

本次 EKS 未产出 pod 级结论：运行环境没有 kubectl，拿不到 pod requests，预订率与装箱全部失效——这比缺 Container Insights 影响更大（后者只挡住第 ⑥ 项）。节点仍然计入分母，只出节点级事实。

闲置与定时停机

除降配外还有两类判定用到同样的利用率数据，但动作不可回滚，所以门槛更硬：采样点数是硬门槛，不走"降置信度"那条分档。

闲置判定（动作：删除）

三条同时满足：

业务时段 CPU p95 < 5%
日均网络     < 5 MB / 日
业务时段采样 ≥ 168 点（硬门槛）

网络口径只认一种：全窗口（业务 + 非业务 + 周末三档全算）按 Sum 逐小时相加 ÷ 窗口天数。

为什么不用业务时段外推全天：实测某实例业务时段外推 53.11 MB/日，全窗口真值 71.62 MB/日，差 26%——那台机器夜里更忙（备份类）。闲置门限只有 5 MB，26% 的口径差足以翻转判定。一台夜间跑批的机器不是闲置资源。

定时停机（动作：停机）

非业务时段与周末两档各自满足三条：

该档 CPU p95  < 5%
该档日均网络   < 5 MB / 日
该档 CPU 峰值  ≤ 20%

输出是候选清单 + 三档实测证据（业务 / 非业务 / 周末各自的 p95、峰值、点数），不是建议。

因为"能不能停"取决于 CloudWatch 看不见的信息：定时任务、被动监听的服务、上游依赖、维护窗口，以及"低利用率"是否恰恰是这台机器存在的理由（冷备）。报告里只会写"停机候选，待确认"，不会出现"建议停机"字样。

这两类判定的第三态很重要："判不了"和"不是候选"必须分开呈现。缺少非业务时段或周末数据时，报告写的是"未评估"，不会写成"无候选"——后者读起来像"已经查过、没有可停的"。同理，一条指标序列整条不存在不等于"恒为 0"：一个 3 小时前新建的 NAT 网关同样会显示"恒 0"，而这一行的动作是删除。

RDS 不建议停实例：停止的 RDS 仍收存储费且最多 7 天后自动启动，所以非生产库的这条路径改为"快照 + 删除"，并在阻断项写明。

托管服务目标：初选与人工审核的分界

本轮判据的另一个主要改进：RDS / Redis / MSK 现在会给出目标规格与月省金额，不再只回答"是不是候选"。改进前这三类的节省额恒为 $0——不是因为没有空间，而是因为判据不选目标。本次两支机队实测，托管层的可优化比例是其按需月额的 23%–30%。

代价是这些目标的性质与 EC2 不同，报告里对应四条硬规则：

  1. 目标是"初选"，人工的角色是审核而不是选型。每条托管建议必带一条阻断项：目标为本 skill 初选，须人工确认变更窗口与回滚预案。
  2. 置信度只有 low 或留空，永远不会是 medium / high。那两档在 EC2 侧的含义是"CPU 与内存两轴都有实测数据"，托管侧没有那个轴，套用等于自造语义。
  3. 摘要单列一行"其中托管服务（目标待人工确认）$X"。它不是第五条口径，而是同一个分子的成分拆分——托管行的金额已经在路线一 / 路线二里面，不能再加一次。
  4. 候选池为空时必须写出六种成因中的哪一条（见前文），不给同一句笼统话。
为什么这个改进不是"变激进了"

加入选型的同时也加入了适配校验，所以它同时删掉了假阳性：实测两个 Redis 复制组（其中一组在本机队）改进前是"降配候选"，改进后变成"已合理配置"——因为校验发现更便宜的候选都装不下当前内存需求，那两行原本的"可省金额"实际是 $0。净效果是少两条假阳性、多一条真实的欠配发现。

四条汇总口径，不制造单一头条数字

报告不给"总共能省多少"的单一数字，这是刻意的。任何单一数字都要求先在两条互斥的降配路线之间选一条，而那是贵方的决定（路线二要逐条确认可接受突发模型），不是本套判据的决定。

落地要求

  • 每条降配建议都附带变更窗口 + 回滚预案要求，不按预设档区分——任何规格变更都需要它们。
  • 托管服务（RDS / Redis / MSK）的目标规格是初选，须人工审核：可订购型号、维护窗口、参数组、以及业务增长预期都在本套判据的视野之外。目标落在价目阶梯最底档的行尤其要按增长预期复核。
  • 存储只能扩不能缩，过度预配的 RDS / MSK 存储只能在下次重建时修正。
  • 内存降配前须自行确认操作系统与 agent 常驻开销能容纳目标内存——报告给出实测值与推算依据，判断权在执行方。
  • Redis 降配前确认数据量增长预期：本判据基于观测稳态，不含业务增长输入。
  • 闲置判定只证明"该窗口内未观察到活动"，不证明可以删除——冷备、被动监听、低频定时任务在指标上都不可见。删除前须核对上下游。
  • 结论可复算：同一份采集数据 + 同一个预设，必然得到同一份结论。报告的原始数据与聚合结果随交付物一并提供。
