## 问题陈述

### P1：`required_*` 拿当前规格去乘测自另一个规格的利用率百分比

整套判据的需求反推是：

```
required_vcpu = max(ceil(cur_vcpu × sus_cpu% / target), ceil(cur_vcpu × peak_cpu% / ceiling))
required_gib  = 同形，用 cur_gib 与 sus_mem% / peak_mem%
```

`cur_vcpu` / `cur_gib` 来自 `describe-*` 的**当前**规格；`sus_cpu%` 等来自
CloudWatch 的**整个 30 天窗口**。这个乘法只有在「窗口内规格没变过」时才成立，
而**没有任何一处校验它**。

若实例在窗口内被改过规格，前一段的利用率百分比是相对旧规格测的，却被当成
相对当前规格。方向取决于改的方向：

| 窗口内变化 | 早期 CPU% 相对当前规格 | 混合 p95 | `required_*` | 后果 |
|---|---|---|---|---|
| 先小后大（扩容） | 偏高 | 虚高 | 虚高 | **低估节省**（偏保守） |
| 先大后小（缩容） | 偏低 | 虚低 | 虚低 | **高估节省** ⇒ 危险方向 |

### P2：检测信号现成，就在已采的数据里

不需要新增任何 API 调用。**同一资源内，某指标的点数明显低于该资源其他指标的
点数**，就说明该指标只在窗口的一段时间内存在。

实测（两支机队，规则取「资源最大 `n >= 600` 且该指标 `n < 最大值的 90%`」）：

| 资源 | 当前机型 | 核心指标覆盖 | 信用指标覆盖 |
|---|---|---:|---:|
| `mysql-pt-01` | db.m6g.xlarge (4 vCPU) | `CPUUtilization` / `DBLoad` / `FreeableMemory` **720/720** | `CPUCreditBalance` 与 `CPUSurplusCreditsCharged` 均 **178/720（24%）** |
| `mysql-pt-02` | db.m6g.xlarge (4 vCPU) | 同上 **720/720** | 同上 **178/720（24%）** |

三条证据合起来指向同一结论 —— **这两台在窗口内被放大过**：
① 核心指标满覆盖 ⇒ 实例整窗口存在；② 信用序列只覆盖 24% ⇒ 只有那段时间它是
burstable；③ 信用余额上限 **576 = 2 vCPU × 20% × 1440**，而当前是 4 vCPU ⇒
上限对应的是一个**更小的**机型。

**方向是「先小后大」，即偏保守的那一侧。** 但这只是这两台的巧合，规则上两个方向都可能。

### P3：另外两条命中是**已被正确处理**的，不算缺陷

同一次扫描还命中两个 ALB 的 `ActiveConnectionCount`（`4/720` 与 `561/705`）。
那属**采集侧**的 VPC 行，`core.py` 没有 VPC 判据；而 `cli-recipes.md §2.6` 的
ALB/NAT 闲置判据**本来就带覆盖度门槛**（「零值序列必须覆盖整窗口才算证据，
一台 3 小时前建的 LB 不算」）。所以那条路径已经在看覆盖度了。

本轮只处理 `core.py` 判据侧的四个服务，不动 §2.6。

### P4：这与「资源新建」是两件事，本轮不合并

`SKILL.md` 的易错项里记着一条未完成项：「『资源新』与『监控缺失』仍未分开」，
采集侧已在采 `created` 与 `new_in_window` 但判据没消费。

那是**所有**指标都短覆盖的情形（实例是新建的）。本轮的信号恰好相反 ——
**部分**指标满覆盖、部分短覆盖。两者的成因、方向、处置都不同，混在一条判据里
会让两边都说不清。本轮只做「不齐」，「全短」留给那条既有的未完成项。

  `describe-db-instances` / `describe-instances` 只返回当前规格，
  CloudWatch 也没有「规格」这个维度。拿不到就不能算，所以只能标注。
  唯一能反推方向的旁证（信用余额上限对应的机型）只对 burstable 成立，不通用。

  那条讲「这份余额测自另一个规格，别拿它否决当前规格」，本轮这条讲
  「本行的利用率百分比混合了两个规格的采样」。重叠但不冗余，那两行客户都该看到。

## 设计

### C1：新增可选输入字段 `partial_coverage`

| 字段 | 必填 | 取值 | 缺失后果 |
|---|---|---|---|
| `partial_coverage` | 否 | 三元组数组 `[[指标名, 该指标点数, 该资源最大点数], …]`。派生规则：同资源 `full-window` 档内，**最大点数 >= 600** 且该指标点数 **< 最大值的 90%** | 不加 blocker（**行为与本轮之前完全一致**，向后兼容） |

**门限 90% 与下限 600 写在采集配方里，不进 `thresholds.json`。**
理由：这两个数只在**派生**时用，`core.py` 只消费结果数组、不读它们。
放进 `thresholds.json` 会造出一个 `core.py` 从不读取的孤儿键，而
`tests/test_no_duplicated_constants.py` 的键覆盖是**双向**的 —— 那会直接把门禁弄红，
且「改 JSON 就能改行为」会变成假承诺。

### C2：一个共用 helper，在四个判据的**最前面**调用

```python
_coverage_note(out, res)
```

**必须在任何早退分支之前调用**，否则 `metric-missing` / `excluded` /
`spec-unknown` 这些早退路径上的行拿不到这条注记 —— 而它们恰恰是最需要解释
「为什么数据看起来怪」的行。

`_verdict()` 已经保证「分支理由排在已追加的说明之前」，所以先 append 再
`_verdict` 的顺序不会被覆盖（该函数的 docstring 记着这个坑踩过三次）。

四个调用点：`evaluate()`、`eval_rds()`、`eval_elasticache()`、`eval_msk()`。
注记文案与服务无关，所以只有一份。

### C3：blocker 文案必须写清三件事

① 哪些指标覆盖多少（可核对）；② 常见成因是窗口内改过规格或中途开启监控；
③ **本判据不改结论，以及为什么不能改** —— 判定方向需要逐小时的规格历史，
describe API 不提供。第 ③ 点不写，读者会以为 skill 已经校正过了。

### 测试影响

**既有 fixture 一律不改** —— `partial_coverage` 是可选字段，缺失即维持原行为。
这是本轮与前三轮的关键区别：前三轮的新字段都是必填、都要改 fixture，本轮不必。

**回归 fixture 不改**，锚定值不变。

新测试要覆盖：① 四个服务各自都产出注记；② **早退路径**（如 `spec-unknown` /
`metric-missing`）上也带注记 —— 这是 C2 那个「必须放最前面」的回归；
③ 反向半：字段缺失或为空数组时**不加**任何注记，且 verdict 与不传时逐字相同。
